# Trusted releases

DEV-505's pipeline is defined in `.github/workflows/checks.yml` and
`.github/workflows/release.yml`. A stable `vMAJOR.MINOR.PATCH` tag whose commit is
on `master` starts a release. No releases are created for pull requests. These
files define the gates; they are not evidence that a live release has passed them.

## One-time setup

Before tagging a production release:

1. Arrange **public** GitHub release hosting. The workflow deliberately refuses
   publication while this repository is private: private GitHub downloads cannot
   serve the unauthenticated update feed. Changing visibility or selecting a
   separate public distribution repository is an operator decision, not automated
   here. Using a separate distribution repository requires adapting the workflow,
   its scoped publication credential, and provenance verification identity first.
2. Set repository variables `DB_AGENT_API_URL` (the public production control-plane
   HTTPS base URL, without a trailing slash) and `DB_AGENT_RELEASE_PUBLIC_KEY`
   (base64 Ed25519 public key). These are public build inputs. No enrollment
   tokens, agent credentials, database credentials, private endpoints, or expiring
   download URLs belong here. URL validation rejects credentials, queries,
   fragments, IP literals, and common local/internal hostnames; the operator must
   still verify that the chosen DNS name really is public.
3. Create a **protected** `release-signing` GitHub environment. Add required
   reviewers, restrict deployments to protected stable release tags, and set its
   `DB_AGENT_RELEASE_PRIVATE_KEY` secret to the private file's base64 text (not
   another base64 encoding of that file). Generate it outside the repository with
   `release-manifest keygen`; retain a secure offline copy. The public and private
   keys must match. No production key is generated by CI.
4. Protect `release-promotion` with required reviewers and stable tag restrictions.
   Configure tag rulesets so only authorized maintainers can create/move release
   tags; protect `master`, workflows, and required checks through repository rules.
   Environment protection is a repository setting, not enforced by YAML alone.
5. Enable GitHub artifact attestations/OIDC and grant the workflow its declared
   permissions. Build, test, signing, and smoke jobs have read-only repository
   access. Only the final promotion job can publish releases and attestations.
6. Run a first tagged release through all native runners and review its evidence.
   Windows Server deployment/reboot drills and full dashboard backup/restore
   qualification remain separate release-readiness gates. Ed25519 update
   signatures are **not** Windows Authenticode/SmartScreen signing or an MSI;
   that packaging is DEV-507.

## Gates and promotion

1. Formatting, `go vet`, workflow/shell lint, Linux race tests, native no-CGO tests
   on all four targets, and disposable MySQL/MariaDB integration tests must pass.
   Native tests inject a stable version and check registration/CLI agreement.
2. A secret-free Linux job uses the exact Go patch version in `.go-version` to
   cross-build `windows/amd64`, `linux/amd64`, `linux/arm64`, and `darwin/arm64`.
   `-mod=readonly`, `-trimpath`, `-buildvcs=false`, explicit CPU baselines, and
   `CGO_ENABLED=0` avoid local paths, dirty-tree state, or host-specific CPU choices.
   Two builds into different directories must be byte-identical. This is an
   in-run reproducibility check, not a claim of independent/hermetic SLSA builds.
3. Pinned Syft scans only the four executables for an SPDX 2.3 SBOM. It does not
   scan the checkout, configuration, or signing directory. SBOM generation must
   succeed and produce packages before signing can succeed.
4. After signing-environment approval, a separate job checks the complete target
   inventory, binary build information, key pairing, metadata and URLs. It signs
   the existing per-target update manifests and the checksum inventory. The private
   key exists only in a restricted runner-temp file, is never passed to a Go build,
   and is removed on exit. A key-material check rejects accidental inclusion in
   release files. Unexpected release files, links, directories, dependency
   replacements, CGO, missing targets/SBOMs, or invalid signatures fail closed.
5. Each native runner verifies the signed bundle and checks the actual executable's
   version, public update key, API URL, toolchain, and platform. The smoke harness
   stages the signed artifact through `update.Client`, with a test-only transport
   supplying local artifact bytes at the unchanged signed URL; it does not relax
   production HTTPS or signature verification. It runs the real baseline binary's
   replacement helper and verifies the resulting version and retained rollback.
   Linux/systemd and Windows Service runners also install/start the baseline,
   require a heartbeat, update/restart the service, require the new version's
   heartbeat, and uninstall while checking config/key preservation. macOS uses
   standalone replacement and a foreground heartbeat without a launchd restart.
   The baseline is built from the same source at `0.0.0`; this does not prove
   migration from every prior release.
6. Only after every smoke job and promotion-environment approval, GitHub generates
   a Sigstore build-provenance attestation covering all signed release files. A
   **draft** release is uploaded, every asset is downloaded again and compared,
   signatures/checksums and artifact provenance are verified, and only then is the
   draft promoted to latest. No feed alias is advanced by this workflow.

A failed signing, test, SBOM, attestation, or download verification step prevents
promotion. A failure after draft creation can leave an unpublished draft for
inspection. Reruns intentionally do not overwrite existing releases or assets;
an operator must inspect and explicitly remove the failed draft before retrying.
Never replace an already-public version's artifacts or retarget its tag.

## Published files and verification

For version `1.2.3`:

| Files | Contract |
| --- | --- |
| `db-agent-1.2.3-{os}-{arch}[.exe]` | Four raw no-CGO executables; `.exe` for Windows only |
| `{os}-{arch}.json` | Existing signed auto-update manifest; see `UPDATE.md` |
| `version.json` | Version, source commit, Go version, public key, public API and immutable artifact base URL |
| `sbom.spdx.json` | SPDX 2.3 inventory of the four executables and their Go dependencies |
| `SHA256SUMS` | Sorted lowercase SHA-256 lines, two spaces, basename, newline; covers all ten files above |
| `SHA256SUMS.sig` | Base64 Ed25519 signature of `fivemanage-db-agent-checksums-v1\n` followed by the exact checksum-file bytes |
| `provenance.sigstore.json` | GitHub's Sigstore attestation bundle covering those files plus the checksum file and its signature |

The provenance bundle is generated after signing and is not in `SHA256SUMS` (no
circular signatures). It is authenticated with GitHub/Sigstore, not the release
Ed25519 key. The pinned agent public key remains the update authority; provenance
does not change the on-machine update protocol.

Obtain the trusted public key independently, not from an unverified download's
`version.json`, then verify the downloaded directory with the source tooling:

```sh
go run ./tools/release-manifest verify-release --dir ./downloaded --public-key '<trusted-base64-public-key>'
gh attestation verify ./downloaded/db-agent-1.2.3-windows-amd64.exe \
  --repo fivemanage/db-agent --bundle ./downloaded/provenance.sigstore.json
```

`sha256sum --check SHA256SUMS` checks integrity only, not authenticity. A plain
`db-agent version` still prints only the injected version; `version --json` prints
the public build settings used by native smoke tests. Registration and heartbeat
use that same injected version.

## Local/offline build and signing

Use the pinned Go toolchain. The build script accepts no private key:

```sh
bash scripts/build-release.sh 1.2.3 '<base64-public-key>' https://api.example.com ./dist
syft dir:./dist -o spdx-json=./sbom.spdx.json
mv ./sbom.spdx.json ./dist/sbom.spdx.json
go run ./tools/release-manifest seal --dir ./dist \
  --version 1.2.3 --public-key '<base64-public-key>' \
  --private /secure/outside-repository/db-agent-release.key \
  --api-url https://api.example.com --commit '<40-character-source-commit>' \
  --base-url https://releases.example.com/db-agent/1.2.3
go run ./tools/release-manifest verify-release --dir ./dist --public-key '<base64-public-key>'
```

Use Syft `v1.55.0` to match CI. Build output directories must not exist; signing
does not overwrite metadata. A partial local failure is not a publishable bundle:
inspect it and use a new output directory rather than reusing mixed outputs.
Offline signing does not generate GitHub provenance or run the promotion gates.

The opt-in smoke harness installs the real `db-agent` system service on
Linux/Windows. Run it **only on disposable machines**, elevated, with no existing
service (the harness refuses to touch an existing/indeterminate registration):

```sh
DB_AGENT_RELEASE_DIR="$PWD/dist" DB_AGENT_RELEASE_VERSION=1.2.3 \
DB_AGENT_RELEASE_PUBLIC_KEY='<base64-public-key>' DB_AGENT_RELEASE_SERVICE_SMOKE=1 \
CGO_ENABLED=0 go test -tags release_smoke -v -timeout=5m ./test/releaseproof
```

These smoke tests do not enroll against production, connect to a real database,
or prove a backup, interactive setup, installer download, or full dashboard restore.
Omitting `DB_AGENT_RELEASE_SERVICE_SMOKE=1` runs standalone replacement only;
the release workflow always enables it on the Linux/Windows service runners.
The public feed/control-plane deployment remains DEV-513, and one-line installer
packaging remains DEV-504.
